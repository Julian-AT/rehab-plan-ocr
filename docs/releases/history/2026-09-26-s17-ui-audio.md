All five failures in the broad run have matching SIGABRT reports in
`AURemoteIO::Cleanup → AVAudioEngine.mainMixerNode → ConversationAudio.attachPlayer`.
The later fresh-simulator preview has the same RPC timeout. A minimal independent
AVAudioEngine player subsequently passes on that simulator. The exact cause is
still unknown; successful isolated reruns do not close the broad audio gate.

The fresh-simulator creation failure is different: its console records an explicit
session cancellation while collecting the title, not an app crash. A separate
EventKit simulator was being booted during that run. Audio service reset/loss
callbacks previously logged the generic `action` reason, so that record cannot
identify the trigger. Those two diagnostic labels are now distinct. The subsequent
serial creation run passes. Do not report this as a confirmed fix or assign a
cause that the original trace cannot prove.

The three current-provider checks cover real spoken-answer presentation, temporal
constraints/“Und danach?”, and typed facts/repeat/pagination. They pass together;
the two remaining checks pass separately. No complete current-build UI pass follows
from combining those runs. Native metadata protections subsequently pass 17 EventKit
tests with one expected file-protection skip.

Two roughly 900-second broad-run delays coincide with macOS clamshell sleep. The
elapsed UI durations are workflow evidence, not p50/p95 application latency. Use
serial simulator sessions for subsequent audio diagnosis, preserve crash reports
and compare awake physical hardware for latency and reliability qualification.
